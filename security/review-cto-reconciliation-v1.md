## Vendor fact checks — opened 9 Nov 2026 PKT
### Supabase recovery copies are not active-row TTLs
[S1 Database backups](https://supabase.com/docs/guides/platform/backups), [S2 Free-plan backup FAQ](https://supabase.com/kb/faqs/platform/free-plan-backups), and current [S3 pricing](https://supabase.com/pricing) search results:
- **Free:** no automatic customer database backups; manual CLI exports possible. No PITR included. This does not establish zero internal provider recovery copies/WAL/deleted-page remnants. Choosing Free is not a privacy-erasure proof and creates a real recovery/data-loss decision.
- **Pro:** daily automatic backups; access to last **7 days**. Team14d, Enterprise up to30d. Daily snapshots may contain a row deleted/expired after capture. SQL DELETE, cron and RLS do not modify old backups. DB backups do not include Storage API objects, so backing up DB metadata is not backing up/deleting image bytes.
- **PITR:** paid Pro+ add-on; physical snapshots+WAL, replaces daily backups;7/14/28-day recovery windows, approximately$100/$200/$400 per month **in addition to plan/compute**. No reason to buy it for this local-only MVP without a separate Founder decision. Retention of SQL/WAL history can exceed application TTL; table-level deletion is not per-row backup erasure.
- Published restore windows are **not an attestation of physical erasure of every provider copy within N days after deletion**. Account-specific plan/settings/export locations and provider contractual deletion terms were not inspected. Do not promise “backups roll off within7 days” as a universal guarantee.

**Recommended decision:** Free, no user-content exports, rebuildable approved schema/catalogue/config only, with explicit Founder acceptance of limited recovery; or approve Pro/recovery retention and the corresponding truthful notice. A strict physical1h/24h erasure promise cannot be confirmed for managed Postgres on current evidence; shorten what is collected, separate access/deletion guarantees, and do not publish that promise. Per-table exclusions cannot be assumed for managed physical snapshots.

**Candidate user copy, conditional on actual chosen configuration:**
> Expiry or deletion stops access through Kitne Ka. Our scheduled cleanup removes active records. Restricted recovery copies may remain under our hosting provider's backup cycle; we prevent deleted or revoked data from becoming accessible after restoration. We do not promise immediate physical erasure of every provider copy.

If verified Pro configuration selected, add:
> Our database provider keeps seven days of recovery backups, which may temporarily contain deleted records.

This describes the recovery schedule, **not** a seven-day physical-erasure guarantee. If no app-managed user-content backups exist on Free, say that specifically after verification; do not claim “there are no copies anywhere.” User/operator/source rights still require approval.

### Cloudflare purge: exact first-party scope, not social recall
[C1 purge API](https://developers.cloudflare.com/api/resources/cache/methods/purge/), [C2 cache-key purge limitations](https://developers.cloudflare.com/cache/how-to/purge-cache/purge-cache-key/), [C3 Workers Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) opened successfully:
- Zone per-URL purge is **POST `/zones/{zone_id}/purge_cache`** with `files` listing **both HTML and PNG**, including every actual host/path/query and relevant custom-key header variant. Scoped `Cache Purge` credential, server-side; plan limits apply. A200/success response means **accepted**, not proof any object existed/was removed; verify subsequent responses and headers. This is documented procedure only; no purge sent.
- `caches.default.delete()` is **local to the invoking data centre**, not global purge. Worker-created custom cache keys cannot generally be purged by single URL; avoid them here. Cache Rules keys may require exact key headers; don't assume dashboard URL purge reaches all variants.
- Revocation must commit first. A late renderer/in-flight response must not repopulate stale cache or return a conditional304 against revoked content. “Invalidate”/stale revalidation is not appropriate for privacy revocation. No-store added today does not evict previously cached responses.
- Launch recommendation: bypass caching for all `/s/*` HTML/PNG, creator responses, errors and aliases; no Cache API put/static-asset/object-store bypass. Route **every HTML/PNG request through the Worker state gate**. Keep cache headers on410/404/503 too. No public production version URL that bypasses the intended controls.
- Provider-subdomain launch (`workers.dev`) has **no verified user-managed zone/purge setup** in supplied plans. Do not assume this zone purge API is available for that hostname. No-cache/state-gated design avoids needing a new domain/purge credential; any previously cached or different-host route needs an explicitly verified remedy before exposing shares.

**Third-party unfurlers:** WhatsApp and X may already hold the HTML-derived preview/`og:image`, and recipients may retain images. Cloudflare controls none of those caches. [WhatsApp official link-preview documentation](https://developers.facebook.com/docs/whatsapp/link-previews/) search results confirm Open Graph image consumption; direct fetch timed out. [X card troubleshooting](https://developer.x.com/en/docs/x-for-websites/cards/overview/troubleshooting-cards) direct fetch returned403; third-party explanations report historical caching, but no current contractual deletion duration or recall mechanism was verified. **Do not promise seven days, instantaneous recall, or that a Facebook re-scrape clears WhatsApp/X.** No messages/posts were created to test unfurls.

**Required share/revoke copy:**
> Anyone with this link can view the published assessment until it expires or you revoke it. Revocation stops new access through Kitne Ka. It cannot remove previews, images or copies already saved by WhatsApp, X or recipients; we cannot promise when those disappear. Keep your management access to revoke the link.

For sensitive assessments, consider a generic OG card without per-check details; a dated public image is inherently copyable. New query/image URLs do not recall old previews and must never resurrect a revoked snapshot.

### Capability leakage is broader than application console logs
[C4 Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) says new Workers enable observability by default; invocation logs include method/request URL, and documents `observability.logs.invocation_logs:false`. Current Free3d/Paid7d logs (pricing changes after1Dec2026); the proposed7d app-log policy is a **maximum**, not proof that free logs provide7d or an audit sink30d. [S4 Supabase logs](https://supabase.com/docs/guides/platform/logs) describes gateway/Postgres/service/error sinks, with retention plan-dependent.

Creator secrets belong only in **Authorization** (or separately reviewed secure-cookie/session design), never URL path/query/fragment, redirects, `poll_url`, `og:url`, `og:image`, error params or analytics. Public opaque share ID is intentionally a **read bearer link**, not a revoke credential; it can still grant access if leaked. Set `Referrer-Policy: no-referrer` on app, private and share pages plus safe external-link attributes; this does not redact provider request logs or eliminate the incoming Referer header.

Hash every high-entropy capability at rest (including tombstone revocation hashes); no raw token in SQL/RPC literals/query filters, DB error detail, request/response logging or tracing. Use vetted hash/HMAC comparison, ≥128-bit CSPRNG secrets, action/resource binding and expiry; don't hash low-entropy passwords with this approach. Scrub Authorization/Cookie/Set-Cookie, token-bearing response fields, URLs/Referer and error context before any app sink. Disable URL-bearing automatic invocation logs where route-template replacement isn't possible; audit Cloudflare access/security/trace exports and Supabase gateway/Postgres statement/error logs separately. Application middleware cannot retroactively redact edge access logs. Use synthetic (never live) tokens/phones to verify every configured sink.
